## 2. Ce qui a marché

### 2.1. Architecture review adversarial 3-couches (Blind + Edge + Auditor)

Les 3 reviewers en parallèle ont produit ~180 findings bruts dont ~60 uniques après dédup. Le ratio noise/signal a baissé d'un round à l'autre — Round 1 : 60% signal, Round 3 : 70% signal — parce que les patches précédents éliminent les low-hanging fruits. **Acceptance Auditor** s'est révélé crucial pour cross-confirmer que les 34 patches Round 2 étaient bien appliqués (33/34 OK, P-19 cosmétique).

**À garder** : pattern adversarial 3-couches + dédup triage + Auditor verification sur les rounds itératifs.

### 2.2. Story split en cours de review (2.3 → 2.3a)

Décisions D1+D2 du code review round 1 ont identifié que Story 2.3 livrait le funnel OTP UI mais PAS : (a) Google Sign-In wiré, (b) Apple Sign-In wiré, (c) ouverture effective session Supabase Auth. Au lieu de réécrire 2.3 ou la laisser en `review` indéfiniment, on a **créé 2.3a** comme story de complétion avec ACs précis.

**À garder** : pattern « extraire une story de complétion » quand un review identifie un scope manquant qui dépasse les patches. Évite à la fois la « story qui ne termine jamais » et le re-planning lourd.

### 2.3. Self-audit brand comme substitut au sign-off humain

DN-1 (audit verbal Alexandre wording CGV/géoloc) résolu en self-audit contre les invariants `project-context.md` (voix Tantie Rose, terminologie canonique, anti-anxiété, pas de mot interdit Contrat §20.1). L'audit a été explicite et traçable, pas un raccourci silencieux.

**À garder** : quand un invariant brand est documenté (project-context, Contrat §20.1), une AI peut faire un self-audit explicite avec checklist publique. Le sign-off humain reste process avant merge `main` mais ne bloque pas le travail tech sur la branche feature.

### 2.4. Pattern « refactor sans dette » sur les decisions

DN-2 à DN-5 ont été résolus par des **vrais fixes code**, pas des defers :
- DN-2 → patch `events.md` immédiat (synchro code/doc)
- DN-3 → décision actée + commentaire `chat-voice.ts` (pas de TODO)
- DN-4 → JSDoc enrichi + lien vers Story future DELETE /me (Cahier §5.2)
- DN-5 → filter sémantique réécrit + test dédié

Aucune décision n'a été trace en defer sous prétexte « on verra plus tard ». Cohérent avec le mandat « pas de dette technique ».

**À garder** : règle « décider = patcher OU documenter explicitement, jamais defer une décision déjà tranchée ».

### 2.5. Local-first + fire-and-forget tenu

Toutes les écritures spawter / palais passent par AsyncStorage **d'abord** puis Supabase en `void saveSpawter(...).catch(...)`. Aucune action user-facing ne bloque sur le réseau (sauf `setSession` qui DOIT être awaited pour ouvrir la session — exception justifiée AC #3 Story 2.3a).

**À garder** : règle d'or « pas d'await Supabase dans une action user-facing » respectée.

### 2.6. CSPRNG strict + anti-replay OIDC

Tous les nonces Google/Apple Sign-In utilisent `Crypto.getRandomBytes(16)` (expo-crypto, CSPRNG natif iOS/Android). Plus de fallback `Math.random()` qui défaisait l'anti-replay. **P-01 Round 3** a corrigé l'erreur initiale (`globalThis.crypto.getRandomValues` non disponible sur RN Hermes par défaut) en passant à `expo-crypto` qui marche partout.

**Pattern figé** : pour tout nonce/secret crypto en RN, utiliser `expo-crypto.getRandomBytes` (sync) ou `getRandomBytesAsync` (async), pas `globalThis.crypto`.

### 2.7. CORS strict via `ALLOWED_ORIGINS` (CSV)

Edge Functions `otp-send` + `otp-verify` reflètent uniquement l'origin si elle est dans la whitelist (env `ALLOWED_ORIGINS`), sinon `"null"`. Jamais `*`. Empêche un site malveillant d'utiliser l'anon key publique pour brûler le quota SMS d'une victime.

**Pattern figé** : Edge Functions Supabase = CORS strict CSV whitelist, jamais wildcard.

### 2.8. Triple gate disciplinée maintenue

5 commits + ~99 patches sur l'epic, **zéro régression triple gate**. Le pre-commit gate a tenu : `tsc --noEmit && lint:vocab && i18n:check && npm test`. 98 tests passants en final, +5 vs Epic 1 (93 tests à la fin de Story 1.8).

## 3. Ce qui a accroché

### 3.1. Round 3 review = surprise — on pensait Round 2 terminer

Round 2 (34 patches + 4 decisions) a été annoncé comme « 95 tests passent, smoke web OK, story → `review` ». La code review Round 3 a identifié 60 findings supplémentaires uniques dont **5 HIGH** (RN Hermes crypto, `updateUserById` no error check, `migrationPromise` reset, CORS fallback ambigu, rate-limit bypass).

**Pattern** : un Round N qui prétend « clean » a typiquement 30-60 findings résiduels. Penser **adversarial-by-default** : tant qu'un round adversarial n'a pas tourné, on n'est PAS clean — on est « clean selon nous ».

**Lesson** : déclencher au moins 2 rounds adversariaux avant tout sign-off humain, surtout sur les stories de complétion comme 2.3a. Le 1er round attrape les gros, le 2e attrape les patterns + le drift entre patches appliqués et description.

### 3.2. Mock statique `isSupabaseConfigured` = test live impossible

P-31 round 3 voulait tester `setSession failure → no router.push`. Bloqué par : `jest.mock("../../src/lib/data-source", () => ({ isSupabaseConfigured: false }))` est **module-level** — on ne peut pas le toggler dans un test isolé sans `jest.resetModules` + ré-import dynamique. Le test a été reporté en defer D-14 round 3 avec note explicite.

**Lesson** : un mock module-level qui doit varier entre tests = **defer testabilité dès la conception**. Pour le futur, utiliser un mock objet mutable ou un getter (`get isSupabaseConfigured() { return mockState; }`) dès le départ.

### 3.3. Email synthétique = trade-off SMTP bounce

Pattern AC #3 Story 2.3a : `auth.admin.generateLink({type:"magiclink", email})` requiert un email — d'où le format synthétique `phone-<userId>@phone.spawt.local`. **Problème** : si SMTP est activé côté projet Supabase, GoTrue envoie un vrai email magiclink vers ce domaine inexistant → bounce → quota SMTP brûlé silencieusement.

D-16 round 2 défère la résolution à « Stéphanie sign-off alpha Termii sandbox avec SMTP désactivé côté projet ». **Pas une option code-only** : alternative serait `auth.admin.createSession` mais ce n'est pas exposé en gotrue-js 2.45.

**Lesson** : Supabase Auth a des trade-offs non triviaux quand on s'écarte du happy path (OTP first-class). Documenter en détail le « pourquoi pas JWT direct » et le « pourquoi pas createSession » dans le README Edge Function (déjà fait pour `otp-verify/README.md`).

### 3.4. RN Hermes ≠ Web crypto

Round 2 P-01 a écrit `globalThis.crypto?.getRandomValues?.(new Uint8Array(16))` croyant que ça marcherait partout. Round 3 P-01 a réalisé que **Hermes (l'engine JS par défaut de RN 0.83) n'expose pas `globalThis.crypto`**. Sur device réel, `generateSecureNonce()` retournait `null` silencieusement → bouton désactivé → toast `auth.error_crypto_unavailable` que l'utilisateur ne comprenait pas.

Fix : refactor sur `Crypto.getRandomBytes(16)` (expo-crypto, déjà dans deps).

**Lesson récurrente** : ce qui marche dans Jest (jsdom + Node crypto) ≠ ce qui marche sur device RN. **Tester sur device avant de cocher un AC qui touche le runtime natif.**

### 3.5. 4 rounds de patches sister stories sans bumper YAML

Stories 2.2, 2.4, 2.5, 2.6 ont reçu des patches **dans chacun des 3 rounds** (Round 1 D1-D4, Round 2 P-22a/P-25/P-30, Round 3 P-19 à P-30) sans que leur YAML status soit jamais mis à jour. Elles sont restées `in-progress` jusqu'au commit `46a9843` qui les a bumpées à `review`.

**Pattern** : quand le travail sur une story se fait via review patches d'une AUTRE story (2.3a touche 2.2/2.4/2.5/2.6 collatéralement), le bookkeeping YAML drift silencieusement.

**Lesson** : à chaque round de code review qui touche plusieurs stories, **propager les status dans sprint-status.yaml** en même temps que les patches, pas après-coup.

### 3.6. P-19 round 2 « functional setter » → P-12 round 3 refactor cosmétique

P-19 round 2 a appliqué :
```ts
let nextAttempts = attempts + 1;
setAttempts((a) => { nextAttempts = a + 1; return nextAttempts; });
```
Fonctionnel grâce à la closure capture + mutation synchrone du setter. Mais Round 3 (Auditor) l'a flag comme « alambiqué, lisibilité dégradée ». P-12 round 3 a refactoré en simple `const nextAttempts = attempts + 1; setAttempts(nextAttempts);` (le gate `submitting` empêche déjà le double-tap).

**Lesson** : un patch « techniquement correct » mais difficile à relire est une **dette future**. Préférer la solution lisible quand elle est équivalente.

### 3.7. Voix Chat post-OAuth → décision structurelle déjà acquise

DN-3 round 3 voulait trancher entre « créer `post_google_signin` / `post_apple_signin` » ou « réutiliser `post_calibration` ». L'analyse a révélé que **aucun écran post-auth ne monte `<ChatBubble />`** (ni `phone.tsx`, ni `otp.tsx`, ni les callbacks OAuth). Le Chat parle uniquement à `palais-reveal` après calibration. La « décision » était déjà tranchée par l'architecture.

**Lesson** : avant de demander « faut-il une nouvelle clé i18n / un nouveau moment ? », vérifier où les consommateurs existent réellement. Le faux dilemme se résout souvent par lecture du code.

### 3.8. Sentinel `null` vs `0` — sémantique non-évidente

Round 2 a introduit `null` comme sentinel skip (P-33). Le filter `(v): v is number => v !== null && v !== 0` excluait à la fois skip ET neutral résolu (value=0). DN-5 round 3 a tranché en `v !== null` strict — le `value=0` (mix posa+néga délibéré) est une vraie réponse délibérée qui doit compter dans la confidence.

**Lesson** : les sentinels ont une sémantique riche. Documenter explicitement les 3 cas (skip = `null` n'incrémente pas, neutral résolu = `0` incrémente, directionnel = `±0.4` incrémente) **dans le code ET dans `events.md`** pour éviter le drift code/doc.

## 4. Découvertes techniques durables

1. **`Crypto.getRandomBytes` (expo-crypto) > `globalThis.crypto.getRandomValues`** pour tout nonce CSPRNG en React Native. Travaille sur Hermes + JSC + web. Pattern figé dans `GoogleButton.tsx` + `AppleButton.tsx`.
2. **Pattern session JWT serveur via `generateLink({type:"magiclink"}) + verifyOtp`** — donne des tokens GoTrue officiels enregistrés en `auth.refresh_tokens`, refresh natif côté SDK. Trade-off : email synthétique nécessaire, SMTP doit être OFF côté projet Supabase ou sandbox.
3. **CORS strict `ALLOWED_ORIGINS` CSV** pour Edge Functions Supabase — jamais wildcard, `"null"` pour origin non-whitelisté.
4. **Promesse mémoïsée pour init asynchrone race-safe** (`migrationPromise` pattern). Tous les appelants `await` la même promesse, reset à `null` sur rejection pour permettre le retry.
5. **Sentinel `null` typed pour skip explicite** (`Record<axis, number | null>`). Distingue « non répondu » (skip = `null`) de « répondu neutre » (value = `0`) de « répondu directionnel » (±0.4).
6. **`setSession` est l'EXCEPTION await user-facing** — toutes les autres écritures sont fire-and-forget, mais `setSession` doit bloquer sinon `finalizeOnboarding` throw `FINALIZE_NO_AUTH_USER`.
7. **`AbortController` + `mountedRef` pattern systématique** pour fetch + setState async. À refs séparées pour onSubmit / onResend (P-13 round 3) sinon collisions.
8. **`capGraphemes(str, max)` utility** pour cap des champs texte (display_name, neighborhood) à 50 graphèmes — ne casse pas les emoji surrogate UTF-16.
9. **Test pattern `mockStackScreen.mock.calls` pour assert `options`** des `<Stack.Screen>` au lieu de `() => null` qui rend la régression invisible (P-21 round 3).
10. **Compensation `unburn()` pour anti-replay OTP avec retry-safe** — burn atomic du pinId, un-burn si provisioning user/session échoue, fenêtre de double-verify mineure acceptée.
11. **`auth_signed_in.demo` flag** uniforme entre OTP / Google / Apple — permet filtrage downstream Kidam (PostHog/Mixpanel) pour exclure le funnel démo des KPI réels.
